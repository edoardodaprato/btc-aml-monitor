The problem

Crypto-asset service providers (VASPs/CASPs) must know whether the addresses their customers deal with are sanctioned, linked to illicit activity or behaving like a laundering pattern, and they must justify that answer to auditors and supervisors.

The approach

Commercial blockchain-analytics tools solve this at scale, but they are expensive and opaque. This project implements the core logic in readable, tested and fully configurable code, so every alert can be explained and every threshold challenged.

How it works

A pipeline of small, independently tested stages. Rules never touch the network: they read a normalised model of transactions and flows.

Screening

Sanctions and labels

The official OFAC SDN list, versioned by publish date and SHA-256, plus your own labels. Every label must cite a verifiable public source; nothing is ever invented.

Exposure

Follow the money

Up to 3 hops in both directions, with pro-rata attribution, time ordering and a weight that decays at each hop. Exchanges and other high-degree nodes are not expanded.

Heuristics

Who controls what

Common-input-ownership clustering (CoinJoin excluded), change detection and structural CoinJoin detection. Every alert that relies on a heuristic says so.

Prices

Amounts in EUR

Each transaction is valued at its historical BTC/EUR price, with ECB EUR/USD reference rates filling gaps. Every price states its date and source.

Traceability

Audit trail per run

Input hash, rule definitions and config hash, sanctions list version, data sources used, and everything that could not be evaluated or was cut by a limit.

Engineering

Built to be adopted

Python 3.11+, typed and documented, configurable in YAML, offline test suite, polite API client with rate limiting, retries and automatic fallback.

Two modes, a control test, one control panel

Start from the customers you care about, or from the blockchain itself, or test another firm's monitoring.

Address mode · scan-addresses

Scores each address 0–100 on its full history with all 21 rules and multi-hop exposure. Writes address_scores.csv, alerts.csv, transactions.csv and the audit log.

Block-scan mode · scan-blocks

Checks every transaction of up to 10 blocks with the rules that work on a single transaction, clusters addresses across the block, and lists sanctioned addresses and their co-spenders for a full address-mode review.

Control test for auditors and supervisors · test-controls

Takes a firm's alert export and tests its monitoring the way an auditor would: data quality, re-performance against an independent Tracery analysis of the same addresses (including sanctioned addresses the firm did not escalate), per-rule escalation rates, backlog ageing, closure quality (too fast, unexplained, copy-pasted, inconsistent) and a reproducible QA sample sized for zero-defect testing. No model, no prediction: every finding points to rows of the file.

Control panel and manual review · btc-aml ui

A local browser page, reachable only from the analyst's computer: start analyses without the terminal, follow their progress, browse past runs and their audit trail, and record a decision on every alert (escalate, false positive, explained) with a note and the reviewer's name. Evidence links open each transaction on a public block explorer for independent verification; decisions are exported as review.csv next to the untouched automated reports, and every run downloads as one Excel workbook with the audit summary, all reports and the review decisions.

Explainable scoring

Each triggered rule counts once: its weight times the strength of its strongest alert. Contributions are summed and capped at 100, then mapped to a band: Low 0–24, Medium 25–49, High 50–74, Severe 75–100. Direct sanctions exposure always forces Severe.

Tracery (project name btc-aml-monitor) is an open-source tool that checks Bitcoin addresses and transactions for money-laundering and sanctions red flags. This guide is for readers starting from scratch and describes version 1.6.0.

1. Installation

You need Python 3.11 or later and Git. In a terminal:

git clone https://github.com/edoardodaprato/btc-aml-monitor.git
cd btc-aml-monitor
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
CommandWhat it does
git clone ...Downloads the project from GitHub

source .venv/bin/activateActivates the environment; repeat it every time you open a new terminal
pip install -e ".[dev]"Installs the tool and the libraries it needs

To check that everything works:

btc-aml show-config
pytest

2. The control panel (no terminal needed)

After the installation, everything can be done from a page in your browser.

Start it. In Finder, open the project folder and double-click start-control-panel.command. (The first time, macOS may ask for confirmation: right-click the file, choose Open, then Open again.) The control panel appears in your browser at http://127.0.0.1:8765/ and the small terminal window can be closed.

It stays on. The first double-click installs the panel as a background service of your Mac: from then on it is always running, starts by itself when you log in and restarts by itself if it ever stops, so a bookmark to http://127.0.0.1:8765/ is enough (useful during a demo). To switch it off, double-click stop-control-panel.command; start-control-panel.command switches it on again. If something looks wrong, the panel writes its messages to output/control-panel.log. From a terminal, the same service is managed with scripts/control-panel-service.sh install | uninstall | status, and btc-aml ui runs the panel in the foreground instead.

The panel is reachable only from your computer: nothing is published online.

Reading a run. The results page shows the score of each address with the reasons, every alert with its explanation, amount and regulatory reference, and warnings when a limit was hit (⚠). At the bottom, the Audit trail shows when the run was made, with which tool version, rules and thresholds, OFAC list version and data sources, plus the full audit_log.json. Download Excel, at the top of the page, gives the whole run as one workbook: a Summary sheet with the audit trail and one sheet per report (scores, alerts, transactions or blocks), with filters on every column; the alerts sheet also contains your review decisions, notes and reviewer. Each original report file (CSV, JSON) can also be downloaded on its own.

Manual review. Under each alert:

  1. Open the evidence links: they show the transactions on mempool.space, a public block explorer, so you can check amounts, dates and addresses independently of the tool.
  2. Choose a decision: Escalate (possible suspicious activity), False positive or Explained, no action.
  3. Write a note with your reasoning (documents checked, customer explanation...) and your name or initials as reviewer, then Save.

Decisions are stored in the run folder as review.json and exported as review.csv (one row per alert, with decision, note, reviewer and time). The automated reports are never changed, so the tool's output and the human decision stay separate, as an auditor expects.

Typical workflow.

  1. Update the OFAC list.
  2. Analyse the addresses of the customer or counterparty.
  3. Read the score and its reasons; open the most severe alerts first.
  4. Verify each alert on the block explorer; if useful, scan the blocks of key transactions.
  5. Record a decision and a note for every alert, then press Download Excel for the file.

Where to find addresses and blocks. Everything on the Bitcoin blockchain is public. A block explorer such as mempool.space lets you search any address, transaction id or block number (the block height; the first block is 0). Good starting points are sanctions press releases (OFAC), court filings and announcements by Europol or the U.S. Department of Justice, which often quote addresses or transaction ids. From an analysed address, open All analysed transactions and press Scan block next to a transaction to check everything else in that block. A random block mostly shows ordinary exchange and mining-pool activity: block scan is most useful when you already know something happened there.

3. Configuration

All thresholds, weights and limits live in two text files that can be changed without touching the code:

  • config/settings.yaml: data sources, request limits, depth of the multi-hop analysis, risk bands.
  • config/rules.yaml: for each rule, whether it is on (enabled), its weight in the score (weight), its severity (severity) and its thresholds (params).

If a value is invalid (for example a weight of 150 or a gap between risk bands), the tool stops with a clear message instead of producing wrong scores. btc-aml show-config prints the configuration in use and its hash, the fingerprint recorded in the audit log of every analysis.

4. OFAC sanctions list

btc-aml update-ofac

Downloads the official SDN list from the U.S. Treasury and extracts the Bitcoin addresses (type "Digital Currency Address - XBT") with the designated entity and the sanctions programmes. It also stores the publication date and the SHA-256 fingerprint of the file: together they form the list version recorded in every analysis.

Run it regularly (for example weekly), because OFAC updates the list often.

Note: the same address can be attributed to several persons or entities. The tool keeps all of them, because every designation matters for reporting.

Adding labels from the control panel

Open Labels in the control panel. You can:

  • add one label: address, category (from a list), source and date, then Add label;
  • import many labels: paste the content of a CSV with the four columns above (for example a spreadsheet saved as CSV), then Import.

Every line is checked: if even one line is wrong (malformed address, unknown category, missing source, invalid date), nothing is imported and the message lists the lines to fix. Labels already present are skipped, so the same list can be imported again without creating duplicates. The page also lists every label you have, with its source.

From a terminal, the same import is:

btc-aml import-labels my_labels.csv

6. Analysing an address

btc-aml analyze <address>

The tool downloads the address history (up to max_tx_per_address transactions), converts every amount to EUR at the price of the day, runs every enabled rule and prints the alerts with their explanation and regulatory reference. A second analysis of the same address uses the cache and is almost instant.

If the history exceeds the limit, the output says TRUNCATED: the oldest transactions were not analysed.

Analysing a list of addresses (address mode)

btc-aml scan-addresses examples/demo_addresses.txt

The file holds one address per line. Blank lines and lines starting with # are ignored, so the file can be annotated. Invalid lines are reported and skipped without stopping the run.

Every run creates a folder output/<date-time>/ with:

FileContent
address_scores.csvOne address per row: score, band, rules triggered, score explanation
alerts.csvOne alert per row: rule, severity, score contribution, evidence transactions, amounts, explanation, regulatory reference
transactions.csvEvery analysed transaction, with net amount, EUR value and the date of the price used
audit_log.jsonAudit trail: date, tool version, input file fingerprint, rule version and parameters, OFAC list version, data sources used, skipped addresses
run.logTechnical log of the run

How the score is computed. Each triggered rule contributes once, even if it raises several alerts: its weight times the strength of its strongest alert (indirect exposure is weakened at each hop). The total is capped at 100. Bands: Low 0-24, Medium 25-49, High 50-74, Severe 75-100. Direct sanctions exposure (R01) always means Severe. The score_explanation column shows the contribution of each rule.

EUR prices. Historical prices come from mempool.space: hourly for recent dates, weekly for older ones (up to 7 days before the transaction), none before July 2010. On some days mempool.space has a USD price but no EUR price: if you have downloaded the official ECB rates with btc-aml update-fx, the tool converts the USD price at that day's ECB reference rate. The btc_eur_price_source column always states which source was used. When no price is available, the EUR cell is left empty.

How to read alerts. An alert is an indicator, not proof. Several rules (fan-in, fan-out, consolidation) also fire for legitimate services such as exchanges: every alert must be read in the context of the customer and the address.

EUR amounts. When no historical price is available, rules with EUR thresholds use the equivalent BTC threshold and say so in the explanation. Structuring (R06) is evaluated only on transactions with a known price, because its thresholds only make sense in EUR.

8. Multi-hop analysis, clusters and change

Multi-hop exposure. The tool follows funds beyond direct counterparties, in both directions: where the money received came from (source of funds) and where the money sent went (destination). Amounts are attributed pro rata: if a counterparty received 25% of its inflows from a sanctioned address before paying us, 25% of what it paid us counts as exposed. Only what happened before (for the source) or after (for the destination) counts.

The weight in the score decreases with distance (hop_decay: 100% at the first hop, 50% at the second, 25% at the third). To avoid thousands of API calls the expansion has limits: number of hops, addresses per hop, transactions per address, maximum time. When a limit is hit, the report says so (exposure_complete = False and exposure_notes).

High-degree nodes. Addresses with a very large number of transactions (above high_degree_threshold, usually exchanges and services) are not expanded: pro-rata attribution through an exchange's shared wallet would be meaningless. They are listed in high_degree_counterparties.

Clusters. Addresses that sign a transaction together normally belong to the same wallet (the common-input-ownership heuristic), and change goes back to the sender. The tool uses this to group the addresses of the same probable entity, excluding CoinJoins. A cluster of thousands of addresses usually means a custodial service (for example an exchange's deposit addresses swept together).

Change detection. Three heuristics, in order of reliability: reuse of an input address, same script type as the inputs, non-round amount when the payment is round. When the case is ambiguous, no output is treated as change.

9. Block scan

Address mode starts from addresses you already care about. Block scan starts from the blockchain instead: it reads every transaction of one or more blocks (at most 10, block_scan.max_blocks in settings.yaml) and flags those that show a red flag on their own.

btc-aml scan-blocks 733459            # a single block
btc-aml scan-blocks 733459 733461     # blocks 733459 to 733461 inclusive

The number is the block height, its position in the chain (the first block is 0). A full block holds 2,000-5,000 transactions and the first read takes about a minute per block, because public APIs return 25 transactions at a time. Later reads use the cache and are instant.

Which rules. Only those that make sense on a single transaction: sanctioned (R01) or labelled (R03) addresses, CoinJoin (R04), payments to many recipients (R09), transfers above threshold excluding change (R14), consolidation of many small inputs (R16) and fees far above the block median (R21). Thresholds are the same as in rules.yaml. Rules that need an address history (structuring, velocity, dormancy...) stay in address mode.

Block clustering (R19). Addresses that spend together with a sanctioned or labelled address, even in different transactions of the same block, are flagged as probably the same wallet. When the cluster exceeds 50 addresses the explanation warns that it is typically a custodial service (an exchange sweeping customer deposits). In that case the sanctioned address is probably a customer's deposit address, and the exchange is the party to contact.

Files produced in output/<run_id>/:

FileContent

A real example. In block 733459 (April 2022) the scan finds two addresses on the OFAC list spending funds, each together with dozens or hundreds of other addresses: the typical behaviour of an exchange collecting deposits. The other alerts in the block (large transfers, batch payments, consolidations) are mostly normal exchange and mining-pool activity. Any block has dozens of them, and they should be read as a list of things to look at, not as established suspicions.

10. Testing a firm's monitoring (control test)

The first nine sections use Tracery as a monitoring system. The control test uses it the other way round: to test someone else's monitoring, as an internal auditor, a second-line reviewer or a supervisor would. It answers the questions behind most enforcement cases on transaction monitoring: are alerts reviewed in time, are closures defensible, does each rule earn its place, and did the system miss anything an independent check would catch?

Input. The firm's alert export, one row per alert, as a CSV file with these columns (download the template from the control panel):

ColumnRequiredContent
alert_idyesThe firm's alert reference
addressyesThe Bitcoin address the alert is about
ruleyesThe firm's rule or scenario name
created_atyesWhen the alert was raised (ISO date, for example 2026-09-01T10:00:00Z)
statusyesopen or closed
dispositionfor closed alertsescalated, false_positive or no_action (common synonyms such as SAR or FP are accepted)
closed_at, reviewer, rationale, txidnoWhen and by whom it was closed, why, and the transaction concerned

Run it. In the control panel, card 4 · Control test: paste the file, optionally choose an address analysis to re-perform against, set the test date and the review deadline, and press Run control test. From a terminal:

btc-aml test-controls firm_alerts.csv --reperform 20261009T223246Z --as-of 2026-10-15

What it checks.

CheckWhat it showsWhy it matters

Every threshold is recorded in the audit log of the run. Findings are prompts for review, not conclusions: each points to rows of the firm's file that a reviewer should open. Nothing is predicted and no model is involved. A firm only result, for example, can mean that the firm has a rule Tracery lacks rather than that it over-alerts.

Files produced in output/<run_id>/: findings.csv, reconciliation.csv (when re-performed), rule_metrics.csv, backlog.csv, data_quality.csv, qa_sample.csv (with empty qa_outcome and qa_comment columns to fill in), audit_log.json and run.log. As for every run, Download Excel puts them all in one workbook.

Try it. examples/control_test/firm_alerts_demo.csv is a synthetic alert file built on the demo addresses. Re-performed against the example address analysis, it shows each kind of finding: an OFAC-listed address closed as a false positive two minutes after the alert, a second OFAC-listed address never alerted, copy-pasted rationales, a rule that never escalates, old open alerts and three unusable rows.

11. Ready-made examples

The examples/ folder contains the results of real analyses and of a control test, so you can look at the files without running anything:

  • examples/address_mode/: the three addresses of demo_addresses.txt (two on the OFAC list and the genesis block address);
  • examples/block_scan/: the scan of block 733459;
  • examples/control_test/: a control test of a synthetic alert file (section 10).

Addresses that are not public for a documented reason (OFAC list or demo addresses) are replaced with <address redacted>. The others belong to ordinary people: publishing them next to an alert would read as an accusation, even though an alert is only a heuristic. Transaction ids (txids) are kept, because they serve as evidence and anyone can check them on a block explorer.

12. Limitations compared with commercial tools

This project shows the logic of a transaction-monitoring system, but it does not replace tools such as Chainalysis, Elliptic or TRM Labs. The main differences:

  • Attribution. The real value of commercial tools is millions of already-labelled addresses (exchanges, services, illicit actors). Here we only know the OFAC list and the labels you import. An address with no known links scores Low even if it belongs to an illicit service.
  • Heuristics make mistakes. Common-input clustering breaks with PayJoin and collaborative transactions, and merges customer deposits when an exchange sweeps them. Change detection is an estimate. Fan-in, fan-out, consolidations and large transfers are everyday activity for exchanges and mining pools. An alert is a lead to investigate, not a conclusion.
  • Limited coverage. At most 200 transactions per address, 20 counterparties per hop, 3 hops, 10 minutes per address, 10 blocks per scan. When a limit is hit the report says so, but whatever lies beyond it is not seen.
  • Bitcoin only, on-chain only. No other blockchains, Lightning, bridges, internal exchange data or Travel Rule messages.
  • Public APIs. Free but slow and rate-limited, with no service guarantee.
  • Prices. For older dates the BTC/EUR price can be up to 7 days old; the date and source are always stated.
  • Regulatory references and thresholds. References are given at section level and should be checked against the official texts; weights and thresholds are illustrative, not calibrated on real data.
  • Not a validated system. There is no model validation, case management, four-eyes review or alert tuning on a real customer base.
